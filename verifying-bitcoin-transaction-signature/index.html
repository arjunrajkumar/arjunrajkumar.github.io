Verifying a Bitcoin transaction signature (Python)

The goal by the end of this is for me to verify the transaction myself for a confirmed transaction. I have chosen this transaction: 29a3efd3ef04f9153d47a990bd7b048a4b2d213daaa5fb8ed670fb85f13bdbcf

This transaction was confirmed in block 153509 on 16 November 2011. It has 11 inputs and two outputs: 50,000 BTC and 500,000 BTC. From these 11 inputs, I will find the highest value input, then check the output related to that, and verify the spend manually via Python. I'm not using Bitcoin libraries such as python-bitcoinlib for interacting with Bitcoin core as the objective is to DIY and learn.

My plan (without AI, before coding)

  1. We are given the transaction ID, and the block height.
  2. From the block height, we get the block hash from our local pruned node itself.
  3. Our pruned node doesn't have access to transactions in the old block.
  4. So, we call getpeerinfo, which lists peers already connected to our node. We are looking for a peer that has NETWORK as the service name, because it means it can supply historical blocks.
  5. Once we find a peer, we request the block from one of those peers.
  6. Once we receive the block, we get the chosen transaction from this block.
  7. We read the transaction’s raw bytes from the block stored locally. The command displayed those bytes as hex text.
  8. We decode the transaction’s hex text into bytes.
  9. From this transaction, we also get all the inputs it accessed to make this transaction.
  10. For this exercise, we choose one input which has the most funds.
  11. So, first, for each of the 11 referenced outputs, we need to get the previous transactions containing these 11 referenced outputs. (We will use the explorer only to find the block hash of each of the 11. The transaction bytes would still come from the peer.)
  12. We fetch any missing blocks from peers. We extract the previous transactions containing the 11 referenced outputs.
  13. For each input, we use its previous transaction ID and output index to find the exact output. We read that output’s amount. We compare the 11 amounts and choose the largest referenced output.
  14. For the largest output, we get the spending conditions for it.
  15. For the largest output, we find the input in the main transaction that referenced it.
  16. From that input, we get the signature and public key it provided to spend the previous output.
  17. So, now we have the spending conditions for the previous output, and the signature and public key from the newer input.
  18. We check that the public key satisfies the relevant condition in the previous output.
  19. We construct the exact message hash for the chosen input’s signature.
  20. We verify the signature using that public key and message hash.

What I learnt

  • The blockchain is a database, but it's not like a normal DB. Instead, it's more like a snapshot to verify that things existed in a state on a previous date. For example, there is no simple query to find which block a transaction exists on! There is no direct lookup that a node can perform. So, Bitcoin Core creates two databases, a UTXO DB (outputs that have not been spent), and an optional transaction index DB. Because I'm running a pruned node, I don't have the transaction index DB.
  • Because of the pruned node, I have to request any transaction, blocks, etc. from peers who are running a full archival node. But I still can't request a transaction from a peer without a block hash.
  • Everything in the blockchain is stored in bytes. The bitcoin-cli and API convert it into hex text while displaying it for me.
  • In a transaction, an input spends a previous output. That previous output held the funds, and it has some spending conditions, which the spender has to pass to spend its funds. The input doesn't contain the amount it spent. It only has a reference to the previous output, which has the amount it spent.
  • When I downloaded Bitcoin Core, it also provided me with an API called JSON-RPC. Basically, I can send a JSON request to my local Bitcoin Core, and it runs it and will return a response.
  • Each block has a block header (80 bytes), which consists of the version (4 bytes), previous block header hash (32 bytes), merkle root hash (32 bytes), time (4 bytes), nBits (4 bytes), and nonce (4 bytes).
